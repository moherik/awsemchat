# Encrypted Circle profile implementation

The approved Circle name, description and avatar belong in encrypted client-owned content. Membership IDs, roles and epochs remain server-visible authorization data. Do not add plaintext profile fields to Circle membership DTOs or use demo names as production data.

## Implemented routing foundation (2026-10-12)

The native envelope and protected Olm plaintext now accept an optional `contentType`: `text` or `circle-profile`. An absent type retains the legacy text contract. Native receive compares the public delivery type with the protected type before committing history. Changing the type rejects the candidate transaction. Exact retry comparisons include the type. Committed-receive proofs include the type when present; legacy proofs retain their original digest contract. Native sent/received archives and the mobile backup wrapper preserve it.

The relay validates the allowed types. A new `circle-profile` event requires a current Circle and an active admin membership, checked while the existing Circle share lock stabilizes membership. Private profile events and ordinary member profile events are denied. The immutable stored envelope supplies the type to inbox delivery; no new plaintext profile column is used. An exact retry of an already committed event returns its existing event and does not grant a new audience.

The mobile sender passes the type to both retry lookup and new native encryption. Incoming delivery passes it to decrypt and commit-proof checks before acknowledgment. Chat projection excludes profile events, including restored sent events, so profile JSON cannot become chat bubbles.

## Avatar integration checkpoint

The encrypted version1 profile accepts `avatar:null` or `{epoch,media:{version:1,id,key,size,mimeType}}`. Exact descriptor fields, object/key/image type/byte bounds and a positive safe epoch are validated. Legacy null profiles remain readable. Different avatars at the same revision conflict rather than selecting an arbitrary picture. Descriptor keys stay in encrypted profiles/history and protected upload metadata, never membership DTOs or plaintext server columns.

Native details provide system photo selection/cropping,512×512 PNG normalization, removal confirmation and saved-photo retry. Prepared uploads retain their intended profile revision and remain recoverable until a matching accepted avatar appears at a later revision. Lost profile replies retry the exact queued profile and avatar epoch; stale unrelated edits/epochs retain the photo instead of replacing newer details. Name/description edits preserve the avatar. Native Circle list/chat header/details display decrypted pictures with rounded-square corners, memory-only data URIs, disabled image caching, loading/retry states and account-change suppression. Feedback uses snackbars; cancelling selection does not announce a save.

Current-profile maintenance and name edits after membership changes upload a fresh encrypted copy for the current epoch. A separate `avatar-refresh` intent cannot replace a selected `avatar-edit` photo. Old grants stay fixed and the new encrypted profile carries the fresh descriptor. The sender fences expected epoch before new native encryption; exact saved outboxes retain their original audience. ## Relay revision foundation

Migration7 adds a bounded `circles.profile_revision`, initially0. New profile envelopes require `profileRevision` in1..9007199254740991; ordinary text cannot carry it. Circle context includes the current revision; profile inbox delivery preserves the immutable event revision. An authorized new profile transaction must propose exactly current+1. Stale and skipped revisions conflict. Profile transactions acquire a per-Circle advisory lock before acquiring the membership share lock, then update the revision and event in the same transaction. This prevents two writers from both upgrading shared Circle locks while competing for the same revision. Exact committed-operation retries are resolved before compare-and-swap and return their existing event.

## Accepted profile selection and recovery

Native export omits outgoing Circle profiles until an accepted relay receipt is committed; the live outbox remains available for retry. Queued ordinary chat messages still export. Received profiles and accepted exported sender profiles carry `profileAccepted=true`, which the backup wrapper preserves. Legacy restored records without that marker are not promoted to current profile metadata merely because they contain a revision.

The profile payload schema is version1: name, description, explicit null avatar. Names are trimmed, nonempty and bounded to80 Unicode scalar values; descriptions preserve line breaks and are bounded to280. Unsupported versions/fields, malformed Unicode/control characters and unsupported avatar descriptors are rejected. These are implementation bounds for the approved editable fields, not completed avatar/media support.

Selection considers marked received/restored profiles or live sender profiles with an accepted event and Sent/Delivered state. It selects the greatest authenticated profile revision independently of local arrival sequence. Conflicting payloads at that revision or malformed newest content return an explicit unavailable state, without choosing a random payload or silently falling back to older metadata. Native Circle list and chat header names subscribe to this projection and keep a generic Circle label when no trusted profile is available.

## Native name and description editing (2026-10-12)

`circle-details.ts` and `circle-details-screen.tsx` connect authenticated member details, accepted decrypted profiles and the account-bound sender. Native Circle chats link to `/flow?view=members&circle=<id>`; invalid identifiers fail closed. Web demo behavior is unchanged. The screen displays member PINs/roles and an admin-editable name/description form, with existing rounded avatars, theme colors, keyboard avoidance, accessible control labels and snackbar feedback. Session expiry prevents mounting the editor. Account transitions suppress late feedback and clear old controller projections.

A new edit fetches current membership, Circle context and native history. It requires current admin membership, a valid accepted local profile matching the remote revision, no queued profile and a nonexhausted safe-integer revision. It sends a schema-validated `circle-profile` at exactly current+1, with a fresh operation ID, through the existing encrypted sender. The relay's transactional admin/audience/revision checks remain authoritative if membership or another admin's revision changes after those reads. The controller does not put profile plaintext in HTTP metadata.

Retry reads the actual queued native outbox record, preserving its operation, payload and revision. It never rebases an uncertain update or overwrites it with another edit. The established sender uploads the exact saved envelope before consulting a new encryption context. A successful background reconciliation removes the pending state on refresh. The screen's Refresh action synchronizes the recipient inbox before rereading details; rendering accepted changes also refreshes the shared history projection. Updates interrupted before native outbox persistence are not promised as saved. Malformed/multiple queued profiles, failed recovery reads and stale/unavailable accepted metadata disable editing.
