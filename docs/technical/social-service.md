# Friendship and Circle service contract

2026-10-11. Owner decisions: contact PIN is fixed; friendship acceptance is mandatory before private communication; Circles contain at most20people including creator; the last admin must select another member before leaving when other members remain. If the creator is the only remaining member, leaving closes the Circle (owner decision, 2026-10-11).

Implemented friendship core: requests address random eight-character PINs, return opaque account/request IDs, and store no phone number or plaintext profile. One canonical account pair has one pending request. Duplicate or crossed requests never accept it automatically. Only its recipient accepts or declines. Repeating the same completed response is idempotent and preserves its timestamp; changing a completed response is denied. Blocking is directional in storage but denies communication and requests in either direction, atomically removes the relationship, and invalidates the old request. Unblocking never recreates acceptance; a fresh request is required.

Every operation checks the current session inside its PostgreSQL transaction. Pair advisory locks serialize request, response and block changes. The accepted-friend snapshot method is useful for reads; future messaging/Circle mutations must share the pair authorization lock within their own transaction rather than trusting a previously returned boolean. RequireAccepted now provides that shared-transaction interface. PostgreSQL tests prove a concurrent block waits for the authorized transaction and future checks reject the blocked pair.

Migration002_social adds friend_links and friend_blocks. The migration runner now applies every embedded version and checks every checksum. Migration003_circles now adds the Circle, invitation and membership-interval ledger; event/media version filenames in the initial roadmap will be reconciled with the actual ordered migration chain rather than changing already-applied SQL.

Evidence: real PostgreSQL17 tests cover recipient-only acceptance, pending authorization denial, mutual blocking, fresh approval after unblocking, old-request replay denial, twenty concurrent crossed requests, invalid/self PINs, revoked sessions and acceptance retries. Full Go suite passes with race detection and vet. The service now provides bounded keyset-paginated accepted, incoming, outgoing and blocked lists. Authenticated social HTTP endpoints are mounted and verified. Request abuse limits, mobile data integration and Circle membership remain incomplete.

List contract: items is always an array, including empty results. Each item contains accountId, fixed pin, status and requestId when applicable; nextCursor is the last returned accountId only when another page exists. Limits are1..100 and cursors are validated opaque account IDs. Profile name, status and avatar remain client-owned encrypted data and are not plaintext columns on the social relay. Lists are snapshots, not permission grants; mutations must call RequireAccepted within their own transaction.

Circle service progress (2026-10-11): Create is authenticated and idempotent per creator/operation ID, creating exactly one initial admin interval. Leave serializes on the Circle row, ends the active interval, increments the membership epoch, and retains archived rows. A last admin cannot leave other members behind; Handoff atomically promotes an existing active member and demotes the departing admin. A sole member may leave, which closes the Circle and revokes pending invitations. Retrying the original creation after closure returns the same closed record and never resurrects membership. Session checks share the mutation transaction. These service methods are not yet mounted as HTTP endpoints. Explicit invitation acceptance, concurrent capacity enforcement, member removal and native encrypted Circle fanout remain pending. PostgreSQL tests cover creation retries, closure/retained intervals, pending-invitation revocation, nonmember handoff denial, transfer followed by leave, and revoked-session denial; the full backend race suite and vet pass.

Circle invitation progress (2026-10-11): active admins can invite accepted friends; the shared friendship authorization lock is held inside the Circle transaction, so blocking cannot race a previously returned permission snapshot. An invitation is pending consent, not membership or a reserved slot. Pending invitations expire after seven days; expired ones are revoked before a replacement is issued. Only the recipient accepts or declines. Acceptance rechecks the inviter is still an active admin and the friendship is still accepted/unblocked, locks the Circle row, and atomically updates its count/epoch with a fresh member interval. Duplicate acceptance returns the same interval only while it remains active; an ended interval cannot be resurrected. Rejoining requires a new invitation and a later joined epoch. Concurrent acceptance enforces20 total members including the creator and returns Circle-full without consuming rejected invitations. Existing shared membership is not automatically removed by friendship blocking. Multiple admins cannot silently take over another admin’s pending invitation. Tests cover explicit consent, admin/friend restrictions, pending/accept retries, blocked/expired/declined denial, fresh intervals on rejoin, and24 simultaneous recipients yielding19 successful joins and5 full responses. Full PostgreSQL race suite and vet pass. Circle HTTP endpoints, member removal, encrypted key fanout and UI synchronization remain incomplete.
