# Identity and device-session contract

Authentication core, local server executable and explicit migration runner implemented and integration-tested, 2026-10-11. Mobile integration remains pending. Preserve SMS-only replacement account access selected by owner. SMS success never decrypts archival history. Native identity/prekey/backup foundations are validated separately; no fake crypto or demo login in production.

Go1.25, PostgreSQL17 integration tests, pinned pgx5.7.6. Auth owns phone challenges, account lookup and active phone session. Raw E.164 phone exists only in request memory and SMS provider call. PostgreSQL stores keyed phone lookup digest, keyed challenge/code digest and SHA256 session-token digest, never raw phone/code/bearer token. Server pepper32bytes is required; losing it breaks lookup/verification and needs deliberate operational recovery. No secret printed in logs.

Challenge target:6digit random code,5minute lifetime,5verification attempts,60second per-phone send cooldown and10/hour per-network bucket. Provider delivery failure cannot yield an accepted challenge; production provider is configured explicitly and absent configuration fails closed. Production transport uses HTTPS; request network identity derives from remote address unless a trusted proxy policy is configured. Owner selected mock SMS first. The development adapter keeps codes in memory for five minutes. POST /dev/otp is available only when explicitly enabled with this adapter and requested from loopback; it is absent from production routing. AWSEM_AUTH_MODE=development-mock is mandatory, and configuration rejects public listen addresses. No real SMS provider is configured or verified.

Successful verification atomically consumes challenge, finds/creates account, increments active device generation, revokes prior session and creates a cryptographically random bearer token. Replayed/expired/exhausted challenges are denied. Active generation is checked on every server request and later transport/media/receipt authorization; token expiry30days. Replacing the phone must not resurrect old membership intervals or old native keys. Public account DTO contains opaque ID and contact PIN only; encrypted profile content is a separate feature, not plaintext status/avatar/name on the relay.

Local test database is a Docker PostgreSQL fixture on loopback55432; credentials are synthetic and never deployment configuration. Each test uses its own schema and cleans only that schema. The explicit migration runner serializes concurrent runs with a PostgreSQL advisory transaction lock, records the embedded SQL checksum and rejects changed migrations. Startup never applies migrations. Readiness checks the checksum and required identity tables. CLI verification uses only the synthetic local test database.

TDD sequence: challenge creation/delivery and persistence; expiration/replay/attempts/rate limits; atomic account/session replacement and token validation; HTTP safe DTO/error contracts; explicit local mock configuration; deferred real SMS adapter; native secure client/session UI integration. No overallTask2 completion until actual provider/device boundary is verified.

SMS-only account restoration does not restore encrypted history without the separate backup key.

Mobile API boundary (2026-10-11): `apps/mobile/src/features/auth/api.ts` now performs challenge, verification, session and logout requests. It validates identifiers, fixed PINs, bearer token shape, device binding, positive safe device generations and future expiration before returning a session. HTTPS is required except explicitly enabled loopback development. Requests have a 15-second timeout, reject redirects and expose only known safe error codes. Verification has no automatic retry because a successfully consumed OTP may have an interrupted response. Tests exercise actual host HTTP sockets; a separate host run completed this client -> local Go -> PostgreSQL verification/session/logout path without printing credentials. This is not Android network or UI validation. Secure session persistence, login routing and replacement-device UI remain pending. Mobile full suite and TypeScript/lint pass; host Node retains pre-existing module-format and experimental-SQLite warnings.

Session ownership and native persistence (2026-10-11): authentication mutations are serialized. Restore revalidates server account/device/generation; revocation or mismatch removes the saved token. Corrupt, expired or wrong-device state is denied before network use. Offline restoration retains known account metadata but cannot authorize server requests. A session becomes ready only after its SecureStore write succeeds; write/delete errors leave a locked state. Tokens are absent from UI snapshots and copied only for authorized transport use. Native vault keys are scoped by a SHA256 digest of the backend origin; the installation UUID is persisted separately and never silently replaces corrupt saved identity. Web has no plaintext session fallback. Actual Android process-restart proof is recorded in `validation/auth/android-session.md`. Approved login UI integration and native crypto/account-generation binding remain pending.

Native account binding (2026-10-11): `bindAccountEncryption` isolates durable ratchets by backend/account/installation/generation and guards retained adapters before and after operations. Android proved initialization, stable reopen and logout rejection. Fresh namespaces initialize explicitly; existing namespaces reopen only after ALREADY_EXISTS, so corrupt or lost existing state is never reset. The eight-native-namespace retention limit remains a lifecycle item for archival migration; this binding alone does not complete replacement-device messaging or UI routing.

Login UI (2026-10-11): native phone/verification entry and `/auth` use `authenticationRuntime` plus the tested login controller. Development defaults to the loopback mock; release requires a configured HTTPS EXPO_PUBLIC_API_URL and has no local mock-code helper. Phone input is normalized to E.164, duplicate submissions are blocked and interrupted challenge/resend retries preserve the operation ID. Verification success prepares account-bound native encryption before the flow becomes ready; failed preparation retries the existing session instead of consuming OTP again. Sign-out revokes and clears authentication before resetting phone/code drafts. Android controller integration and the rendered entry screen are recorded in validation/auth. Whole-app production routing, social/chat transport state and direct control interaction acceptance remain pending.
