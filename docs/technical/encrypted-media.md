# Encrypted media foundation

The owner confirmed Supabase is not configured and selected local integration/testing first. This does not authorize creating a paid provider project or claim that provider permissions work.

`apps/mobile/src/features/media/encrypted-media.ts` prepares bounded media using the existing authenticated archive codec, with an injectable ciphertext-storage interface. It accepts JPEG/PNG/WebP/GIF byte arrays from1 byte through2 MiB. Bytes are copied before asynchronous encryption, split into16 KiB chunks and wrapped with an authenticated manifest containing object identity, MIME type, byte size and chunk count. Native archive account/context binding uses a media-specific object context, separate from history backups. The wrapper's record audience is an internal object-context marker, **not a Circle authorization grant**.

The private descriptor contains the recovery key and is intended for the encrypted message/profile channel. Storage receives only opaque object identity and authenticated ciphertext; it receives neither plaintext bytes nor the recovery key. No descriptor or plaintext is persisted by this module. Upload authenticates the prepared archive before handing it to storage. Retry uses the same prepared ciphertext and identity; the storage port must reject conflicting overwrites. Prepared-object session ownership is held in memory rather than serializing bearer/session data. Account transitions are checked after every asynchronous boundary, before uploading and before returning decrypted bytes.

Download validates descriptor bounds, ciphertext limits, object binding, the authenticated manifest and exact ordered record/chunk layout before returning any bytes. It rejects wrong keys, substituted objects, truncation, reordered chunks, incompatible metadata, wrong lengths and noncanonical base64. It does not guess partial media or publish an unverified prefix.

### Protected upload recovery checkpoint

`upload.ts` serializes operations sharing one vault, persists prepared intent before HTTP, and retains uploaded completion until explicit acknowledgment. The original Circle, epoch, object descriptor and ciphertext cannot be replaced while pending. Lost upload replies retry those exact values, rather than adopting a newer audience. `encrypted-media.restore` authenticates the complete persisted archive before admitting it for upload. Loaded completion is authenticated before returning its descriptor. Acknowledgment is intended only after the consuming encrypted profile/message operation has committed; it does not itself publish a profile/message.

`upload-vault.ts` keeps ciphertext in a private file and a bounded2048-character descriptor/pointer/digest record in the protected metadata port. File integrity, immutable job identity and monotonic completion are validated. Pointer writes whose result is uncertain retain referenced ciphertext; clearing removes the protected pointer before deleting ciphertext. Orphan files after interrupted pointer creation/deletion still require cleanup. `upload-storage.native.ts` uses the installed Expo57 File/Directory APIs and SecureStore with a dedicated keychain service and WHEN_UNLOCKED_THIS_DEVICE_ONLY accessibility. Only encrypted bytes enter files; keys remain in SecureStore metadata. The nonnative adapter requires native storage rather than falling back to browser plaintext persistence.

`account-circle-media.ts` and the production authentication runtime expose `circleMediaUpload(circleId)` through the actual native archive bridge, HTTP adapter and vault. Persisted fingerprints include API origin, account, device, generation and Circle; full session/token/readiness changes retire open controllers. Fingerprints exclude bearer tokens so a legitimate same-generation restart can reopen its own intent. The production UI does not call this supplier yet; avatar/collection wiring is next.

### Circle authorization gateway checkpoint

Migration10 adds immutable Circle object claims (owner, original epoch, ciphertext digest and size) and grants bound to exact membership intervals. `media.Service` uses the existing Circle/session transaction owner to hold the current audience stable while storing ciphertext and committing the claim/grants. New uploads require the current epoch. An exact original-owner retry remains valid after other members join, but never adds grants; changed content/epoch conflicts. Current membership and the original interval grant are both required for reads. Removal, rejoin under a new interval, Circle closure and session replacement deny access. Download also checks stored bytes against the database digest/size. Keys and plaintext MIME/captions never enter these tables.

Optional local server activation uses the absolute `AWSEM_MEDIA_LOCAL_ROOT` environment path, a private service-owned directory. Without that setting, media routes are not installed. Authenticated routes are `PUT /v1/media/circles/{circleID}/objects/{objectID}?epoch={originalEpoch}` and `GET /v1/media/circles/{circleID}/objects/{objectID}`. Uploads contain opaque ciphertext bytes with `Content-Type: application/octet-stream`, bounded to8 MiB; downloads return the same bytes with no-store/nosniff headers. The current client archive uses canonical base64 text; its future HTTP adapter must preserve those bytes exactly. Errors are bounded public codes: INVALID_INPUT400, SESSION_REVOKED401, DENIED403, OBJECT_CONFLICT409, MEDIA_TOO_LARGE413 and UNAVAILABLE503. No key query parameter or client-supplied audience is accepted.

Storage publication precedes database commit, so a storage/commit failure can leave an unreadable orphan. The claim/grants roll back; exact retry can reuse the immutable bytes. Orphan cleanup is still required. Authorization locks currently span the bounded local file operation; a remote provider adapter must preserve the authorization invariant without unbounded provider latency. This gateway is Circle-only; private-chat/personal media authorization remains open. It does not authenticate the archive itself or prove an uploaded object was referenced by an accepted encrypted event. Encrypted descriptors must still be published through the authorized message/profile owner.

### Operation-bound cancellation and durable cleanup (2026-10-14)

Migration14 adds one shared account-generation-operation lock, permanent cancellation tombstones, exact operation ownership on new media claims and a durable per-object cleanup queue. Relay sends, uploads and cancellation take the same lock. Cancellation returns the already committed event when send won; otherwise it fences future send/upload attempts and schedules deletion for that operation's objects. Reads are denied once the cancellation transaction commits. The worker retries bounded local-storage deletions across process restarts, and absent files count as deleted. Legacy claims remain readable and are excluded from guessed cleanup.

The mobile authenticated storage adapter now includes the relay operation on each Circle media PUT and exposes operation cancellation. Protected upload state saves the immutable operation and `uploadAttempted=true` before PUT. Confirmed cancellation clears the job; uncertain results preserve it for exact retry; committed events preserve and reconcile the media. Avatar edits persist a `profileIntent` and reuse its operation for publication. Collection refresh computes conservative part boundaries first, saves the matching part operation on each media upload, and passes those operations to the snapshot publisher. Chat photos, Moments, shared stickers and one-off stickers retain their existing operation binding.
