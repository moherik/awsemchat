# Private profile delivery

Private profiles are encrypted chat metadata shared only through an accepted friendship. The relay stores and routes ciphertext; it must not receive a display name, text status, avatar key, or playback detail in plaintext. Friend PINs remain the public contact identifier.

The owner can set one display name and one current text status. A private chat and accepted-friend surfaces show the latest authenticated profile received for that friendship. A profile update is a control event, never a chat bubble, and is selected from accepted history by that conversation's authenticated delivery order. An unaccepted, blocked, or ended friendship does not receive new updates. A later friendship audience starts with a fresh profile update and cannot reuse controls from an earlier audience.

Circle status is visible to every current Circle member, whether or not the members are accepted friends, per the owner's explicit product decision. The Android client sends the current name and status in a separate `circle-member-profile` event encrypted to the exact current Circle audience. It is not forwarded from private-friend profile events and never appears as a chat bubble. The receiver resolves the highest valid profile revision for the sender and current membership epoch; equal-revision disagreement or malformed data fails closed. Membership changes create a new audience epoch, and a profile sync republishes the latest snapshot for that epoch so new members can see current profiles without receiving earlier content. The owner's own status stays hidden from their Circle bubbles. Now Playing remains accepted-friends-only and never appears in Circle bubbles.

The current text profile format is version 1. Version 2 adds an `avatar` field containing either `null` or a validated encrypted-media descriptor. The descriptor is sent only inside the end-to-end encrypted profile event; it is never sent to the relay as plaintext metadata. Legacy version 1 profiles remain readable. A same-revision disagreement in any field, including the friend-scoped avatar descriptor, is a conflict and must fail closed.

Private-photo publication is implemented at the client level. The Android client stores the source photo and each friendship's pending publication in dedicated encrypted SQLCipher data, scoped to the active account/device/generation. Its profile controller loads, replaces, or clears the source photo; text-only profile edits preserve the current photo mode. For every accepted friendship, the client prepares a distinct immutable encrypted media object and descriptor bound to that friendship's conversation, audience, and profile operation. It saves ciphertext and profile intent before upload, retries the same upload and event after an uncertain result, and drains an older pending revision before publishing a newer one. Removing a photo publishes version 2 with `avatar: null`. Missing/corrupt source data or a changed friendship audience blocks publication rather than silently removing the avatar or widening its audience. The Android editor now uses the system photo library, crops to a square, resizes/compresses on device, and supports replacement and explicit removal. A shared rounded-square avatar view renders the current private photo in the profile, Friends list, new-conversation picker, chat list, private chat header, and conversation details. Remote bytes are downloaded and decrypted only after validating the current accepted friendship and account session; failures expose a retry control. Android device acceptance and live media-provider acceptance remain open. Spotify/Now Playing integration remains subject to its existing Android/provider feasibility gate.

The existing private message relay supplies the necessary audience boundary: each event is bound to the accepted friendship conversation and its immutable `friend:<request-id>` audience. The client sends a `private-profile` event through the ordinary native encryption/outbox path to exactly one accepted friend. It is accepted by the relay only in a private conversation with one original recipient and is filtered from Chat projection. Profile edits and retries preserve operation identity and never broaden the recipient set.

## Verification

- Strict profile parsing rejects malformed, oversized, unknown-field, and invalid Unicode data.
- Latest-profile projection considers only accepted `private-profile` history in the exact friendship audience, rejects conflicting same-sequence values, and keeps profile control events out of Chat bubbles.
- Relay authorization accepts private profile events only for a currently accepted private friendship, while rejecting Circle and nonfriend routes.
- Native exact retry preserves the profile operation, audience, and plaintext; inbox refresh after acceptance supplies the same encrypted profile to the intended friend.
- New-friend, ended-friend, block, offline retry, and account-replacement transitions do not leak a profile into another audience.
- UI coverage exercises local photo selection/replacement/removal and profile-photo rendering in each Android friend/chat surface, including failed-first verification of the previously neutral-only surfaces.
