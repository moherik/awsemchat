# Production Circle membership

The native details screen uses member PINs/roles and the shared popup-menu component. Removal, admin handoff and leaving require a second explicit confirmation. The confirmation binds the displayed epoch and actor/target membership intervals; changed/rejoined memberships require a fresh confirmation. The only remaining admin must transfer the role before leaving other members. Leaving alone closes the Circle and revokes pending invitations.

The separate invitation page uses real paginated accepted-friend data, PIN search and checkboxes, excluding existing members. Selection is bounded by current remaining capacity; invitations do not reserve slots or imply acceptance. Successful invitation acknowledgments remove only those peers from selection. Lost responses retain unfinished peers; the server reuses their pending invitations. Roles and friendship consent are rechecked transactionally. Selection is memory-backed; restarting the selector requires selecting peers again, while existing remote invitations remain intact.

## Guarded mutations

`POST /v1/circles/{circleId}/membership-operations` accepts `{operationId,action,actorInterval,expectedEpoch,targetId?,targetInterval?}`. Action is leave/remove/handoff; leave forbids target fields, other actions require them. Actors come exclusively from the current authenticated session. New operations require the exact current epoch and membership intervals, plus existing role/handoff rules. Migration8 stores a request digest and immutable result keyed by Circle/account/operation. Circle row locking serializes mutations and retry lookup. Exact retries return the original result, including after a member leaves/rejoins or a Circle closes. Changed requests return409 OPERATION_CONFLICT; stale intervals/epochs return409 MEMBERSHIP_CHANGED. Legacy endpoints reuse the same transaction mutation owners but do not supply the guarded-operation contract; production controls use the new endpoint.

Native membership intent metadata is small and stored in device-only SecureStore, scoped by API origin/account/device/generation/Circle fingerprint. Bearer tokens remain in memory. Shared vault owners serialize controllers. Confirmed immutable operations are persisted before HTTP and their results remain until acknowledgment. Failed or uncertain storage never justifies a fresh replacement operation. The result can be recovered even when Circle details are no longer readable after leaving. Account/token/generation changes prevent a retained controller from acting.

`POST /v1/circles/{circleId}/membership-operations/cancel` accepts the same exact request. Under the same row lock it returns an already committed result or persists a cancellation fence. A later mutation of a fenced operation returns `cancelled:true` without changing membership. Cancellation never reverses a completed action, and a payload mismatch never cancels another request. Migration9 adds the fence marker without rewriting migration8. The UI explains these consequences before cancellation and acknowledges only the persisted result. Ordinary network failure is never interpreted as proof that the action did not commit.

## Current profiles after membership changes

Foreground maintenance scans at most five Circle summaries per pass, with cursor continuation and single-flight execution. Only admin summaries invoke current-profile sharing, and actual membership/admin/context/revision checks run again before sending. A valid accepted profile in an older epoch is republished as a new encrypted next-revision event to the current authorized audience. Already current-epoch metadata produces no broadcast. Queued profile retries retain their original operation; stale/rejected queues remain protected until the separate native/server retirement work is complete. New members receive the fresh event, without prejoin messages or Moments. An admin must be online with the accepted profile and usable recipient keys. Multiple admins remain protected by relay revision serialization, but permanent conflicting queued-operation recovery is unfinished.

## Evidence and limits

Test-first client cases cover exact request/result DTOs, pre-HTTP intent persistence, lost replies, account replacement, admin/self-removal/handoff/closure guards, stale confirmations, cancellation and invitation selection. PostgreSQL tests cover exact retry after closure, remove/rejoin protection, wrong request/interval/epoch, strict authenticated HTTP, cancellation fencing and cancellation/commit races. A real inbox regression proves prejoin profile exclusion and fresh-current-profile delivery, and rejects a removed audience. All286 mobile tests, TypeScript, uncached lint,43 native Rust tests, full PostgreSQL race suite and vet pass.

The activated local8088 service has migrations1–9. Actual typed clients/controllers with three synthetic accounts passed consent, guarded lost-response retries, cancellation, handoff and closure through that socket; synthetic sessions were logged out. This substitutes memory at the host vault boundary, so it does not prove native SecureStore process-death recovery. Emulator controls, native themes/keyboard/TalkBack, actual two-device delivery, avatars, encrypted shared collections, capacity/retirement lifecycles and provider acceptance remain required for complete Circle/MVP acceptance.
