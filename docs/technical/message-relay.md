# Encrypted message relay contract

Task 6, author-only private and Circle message deletion, is implemented through migration016 and verified with PostgreSQL integration tests. The broader relay protocol below is still an incremental production implementation; separate-device acceptance and remaining product integrations remain open.

## Wire schema

The relay consumes the exact native durable outbox JSON: version1, operation, conversation, audience, sender Curve25519/Ed25519 public identities, and recipient entries containing peer account ID, recipient public identities and `{kind,body}` ciphertext. Kind0 is an initial Olm message and kind1 is an established-session message. Ciphertext is canonical unpadded standard base64. Public identities decode to32 bytes each.

Identifiers contain1..128 ASCII letters/digits or `._:-`. Packets are capped at2MiB, each ciphertext body at65536 encoded characters, and recipient count at19, matching the maximum other members of a twenty-person Circle. Native request limits and overall account/history capacities remain separate limits. This packet cap allows fanout of the native32KiB plaintext limit without assuming that native output has the same bound as one native input.

Unknown fields, explicit plaintext fields, unsupported versions, duplicate peers, missing/null message kinds, malformed keys/base64 and empty recipients reject. The server validates structure and authorization; it cannot authenticate an Olm ciphertext by decrypting it. A syntactically valid opaque body still requires native signature/pin/session/MAC/context validation on the recipient. Server logs must not contain bodies or credentials.

## Transactional persistence

The sender account/device/generation comes from the bearer session. Its public identities must match the registered current generation. Every recipient's public identities must match that account's locked current generation. Authorization and assignment to delivery queues share the transaction with the existing authentication/friend-pair/Circle locks.

Private conversation IDs are derived from SHA256 of the domain-separated, canonical ordered account pair; the audience identifier is `friend:` followed by the current accepted friendship request ID. Circle conversation IDs are the Circle ID and audiences are `circle:` followed by the current epoch. The service supplies these identifiers for native encryption. Send rechecks the context inside its own transaction rather than accepting the earlier snapshot as authorization. Context HTTP/mobile integration is still required.

Circle submissions must contain exactly the current members except the sender. Store the original recipient generations and membership intervals. A later join or rejoin must not acquire an earlier queue entry; removal must prevent future delivery. Private queues must retain the original accepted friendship interval so a new friendship cannot revive an old access grant.

Migration006 stores events and generation-bound recipient delivery entries. Send uses the native operation as the sender-generation idempotency key and stores a digest of exact outbox bytes, which include the encrypted routing context and immutable recipient set. Identical committed retries return the same event without creating delivery entries; changed retries conflict. An already committed identical retry only acknowledges the existing event and does not grant new delivery access, even if membership has changed. A new send must pass current authorization. Receipt acknowledgements never mean that the sender can replace the original ciphertext or recipients. Generation changes cannot silently re-encrypt pending messages.

The service currently returns `sent` after commit and leaves every delivery acknowledgement unset. Circle recipient entries retain their original membership interval and generation. Private event audiences retain the accepted friendship request identifier. Inbox fetching now revalidates those grants; recipient acknowledgement is now implemented, while native activation is still pending.

## Context/send HTTP and mobile contract

`POST /v1/messages/context` accepts exactly one of `targetId` or `circleId`, with a4096-byte body limit. It returns conversation/audience identifiers, sender public identities and recipient account IDs, generations/public identities and Circle interval IDs when applicable. Circle responses also include circleId/epoch. These are current authorized snapshots, not reusable authorization grants.

`POST /v1/messages` accepts `{ "envelope": "exactNativeOutboxJson" }`, with a4MiB outer request limit and the2MiB decoded envelope limit. Success returns200 `{ "id": eventId, "operation": nativeOperation, "status": "sent" }`. Both endpoints derive the actor from exactly one bearer header, reject unknown fields/null bodies/trailing JSON/query parameters, and disable caching. Fixed error codes include401 `SESSION_REVOKED`,400 `INVALID_INPUT`,403 `DENIED`,409 `OPERATION_CONFLICT`,503 `KEYS_UNAVAILABLE` or `UNAVAILABLE`.

The mobile message API is exposed by the authentication runtime. It validates context routing, current Circle epoch/audience, recipient generations/intervals, canonical public-key shape and uniqueness. It sends the outbox string unchanged. Send acknowledgements must match the requested operation and report only `sent`; a `delivered` response cannot be inferred from submission. Session changes suppress responses, redirects/unsafe origins reject, and requests use a15-second timeout. The native queue/controller and chat UI consume this API.

## Message deletion (migration016)

`POST /v1/messages/redactions` accepts either a committed `eventId` or the complete legacy identity descriptor. Only the authenticated author account may delete its own private or Circle Chat event; Circle admin status grants no additional authority. The server commits the redaction idempotently, clears the event and each delivery ciphertext while retaining delivery sequence metadata, and records an account-scoped redaction entry for the author and immutable original recipients. Current Circle membership is never used to expand that audience, so members who join later cannot discover earlier deletions. Inbox, status, exact-send retry and event-bound media reads enforce the redacted state.

`GET /v1/messages/redactions` returns identity descriptors only, never message content, and only for entries visible to the authenticated author/original recipient account. Mobile sync applies these pages to encrypted local history before inbox refresh and advances its native cursor atomically with the page application. Lost delete responses retry the same target/operation. Local content is removed only after server confirmation; pending deletes survive offline and are retried. A best-effort encrypted notice is routed only to the original recipient set and is not a chat row. Server migration/deployment on a production host and multi-device acceptance remain release gates.

## Delivery stages and remaining decisions

`GET /v1/messages/inbox?cursor=eventId&limit=25` returns `{ items: [recipientDelivery], cursor?, more }`. Limits are1..25. Each item contains only its recipient's ciphertext, sender account/generation/public keys, recipient public keys and immutable routing identifiers. The response does not expose the other recipients. Cursors are event IDs belonging to the authenticated account generation's own queue; global sequence values are not exposed. Invalid, foreign and repeated query parameters reject.

The service scans a bounded page and rechecks each candidate's current original grant. Private messages require the same accepted friendship request and no block. Circle messages require the recipient's original membership interval to remain active; leaving/rejoining cannot revive an old interval. Candidate authorization uses separate transactions to avoid retaining friend-pair locks while waiting on Circle locks. Cursor progress includes skipped denied candidates so inaccessible entries cannot permanently stall synchronization. Fetching never sets delivered_at.

Send acquires recipient-generation queue locks in sorted account order before assigning delivery sequences, and holds them through commit. This prevents a later committed message from advancing an inbox cursor past an earlier uncommitted entry. A controlled PostgreSQL trigger test first reproduced that missing-message bug, then passed after the ordering fix.

The mobile inbox client uses GET only, validates bounded recipient payloads and canonical ciphertext shape, rejects duplicate events/stalled cursors, strips unrelated fields and emits no acknowledgement. Native decryption/commit and persistent cursor integration remain required.

Local native ratchet/outbox commit means queued. Server commit means sent. Recipient acknowledgement is emitted only after native decrypt/inbox/history commit, and means delivered. Fetching or viewing must never emit a read receipt. Reconnect/replay must produce one local message; already committed native receives need a safe way to resume a lost delivery acknowledgement without decrypting twice.

Circle delivery requires acknowledgement from every original recipient. A member leaving or being removed never shrinks that set; an unacknowledged original recipient keeps the message Sent. This policy was explicitly confirmed on 2026-10-12. The queued/sent/delivered product stages and delivery-only receipts remain required.

Remaining implementation: sender interval/provenance integration for future Moments; additional audience/generation race tests; persistent cursor and product synchronization; background/incremental synchronization/realtime; offline expiry/retention with stable cursor semantics; native generation/key retirement; two separate device acceptance and UI connection. In particular, native `REPLAY` currently identifies an existing sender/operation in history before checking the incoming ciphertext; it is not sufficient proof for acknowledging a replayed delivery. Exact committed-receive matching must be implemented before acknowledgement recovery is activated.
